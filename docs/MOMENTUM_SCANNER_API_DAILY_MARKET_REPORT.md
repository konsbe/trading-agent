# Momentum Scanner — API Service Spec, Addendum: Daily Market Report

**Extends:** `docs/MOMENTUM_SCANNER_API.md` / `services/data-analyzer/cmd/momentum-api`.
**Status:** specification. Nothing described here is built yet.
**Serves:** `web-app/ui/mfe-market-report`'s "Daily Market Report" screen.

**This addendum touches a different subsystem than every prior one.**
The candidates/watchlist/tracked/backtest-lab/data-source endpoints all
read `momentum_*` tables built and verified this session. This report is
generated by `marketcycle`, `macrocorr`, `additional`, and
`data-macro-intel` — existing packages in `data-analyzer` and
`data-ingestion` that predate the momentum work and have only ever fed a
Discord embed (`reports/builder.py`). **Do not assume these packages
already support what this addendum asks for.** Verify first.

---

## 0. What this endpoint is, and is not

**Is:** a JSON reshaping of the existing daily market report, split into
a **global section** (macro/monetary/growth/inflation/geopolitical —
market-wide, not tied to any one instrument) and a **per-instrument
section** (price facts, and where supported, market-cycle phase and
intermarket correlation) for a fixed instrument list plus the user's
live watchlist.

**Is not:** a new analysis engine. If a metric isn't already computed
somewhere in the existing Go packages, this endpoint does not invent it.
Where the underlying package can't yet be pointed at an arbitrary
symbol, that's a real, separate piece of work (§1.1), not something to
route around.

**Preserve the existing honesty pattern.** The current report's "HTML
coverage" section marks categories `not_automated` / `needs_data` /
`partial`. Carry this through unchanged — don't quietly drop it because
it's less flattering than the rest of the report.

## 1. What's actually per-symbol today, and what isn't

From the pasted report and its footers:

| Section | Scope today |
|---|---|
| Macro (VIX, 10Y, EUR/USD), monetary policy, growth cycle, inflation, global/geopolitical | **Market-wide.** Not tied to any symbol. Unchanged by this work. |
| Market cycle (`mc_market_cycle`) | **One hardcoded symbol**, via `MARKET_CYCLE_*` env vars (confirmed by the footer: "320 daily bars · MARKET_CYCLE_* in .env"). |
| Macro correlations regime (`mc_macro_correlation`) | Market-wide regime label, but its **flags** (e.g. `usd_strong_em_headwind`) may be computed against the same single configured symbol — verify. |
| Intermarket (bond–equity, oil–equity, VIX–equity ρ) | Each pair is **hardcoded**: one bond proxy, one oil proxy, VIX, all against one benchmark equity. |
| Seasonality, presidential cycle | Market-wide calendar facts, not symbol-specific. Unchanged. |
| Earnings calendar entries | From `BOT_EQUITY_SYMBOLS` (the hardcoded list — AMZN, INTC, XOM, GOOGL, MSFT in the sample). |

### 1.1 What this request actually requires, stated plainly

Two of those rows need real code changes, not just a new HTTP handler:

1. **`marketcycle`'s compute function needs to accept a symbol
   parameter** instead of reading one configured value, so it can run
   for S&P, gold, oil, and Shell independently. **This does not apply to
   the three Treasury yield instruments** — a yield series has no price
   phase, drawdown, or 200DMA; market-cycle output is only meaningful for
   equities/ETFs (§2.2).
2. **`macrocorr`'s intermarket pairs need the same treatment** if any
   pair is meant to run per-instrument rather than staying as one
   market-wide reading. Given the pairs are already bond/oil/VIX-vs-one-
   benchmark, the more honest design is likely to **keep intermarket as
   one market-wide reading** (it's answering "how are bonds/oil/VIX
   behaving relative to equities generally," not a per-instrument
   question) and not force it into the per-instrument loop at all. Decide
   this explicitly in step 1 of the build order — don't default to
   "loop everything" without checking whether the metric even makes
   sense per-instrument.

**The earnings calendar** is more straightforward: swap
`BOT_EQUITY_SYMBOLS` for the new instrument list's equities plus the live
watchlist. Yield instruments have no earnings and are excluded from this
section by construction.

## 2. Endpoint

```
GET /api/v1/market-report/today
```

No parameters. Latest generated report.

### 2.2 Field notes

- **`type` decides what's shown.** `treasury_yield` instruments get a
  `yield` object and `market_cycle: null` always — never attempt a price
  phase or drawdown for a yield series, that's a category error, not a
  data gap.
- **`unavailable_reason` is required whenever `market_cycle` or `price`
  is null for an equity/ETF instrument**, same pattern as every other
  addendum's honest-absence handling. Never silently show an empty card.
- **The fixed instrument list is exactly seven entries**: S&P (SPY),
  Gold (GLD — confirm exact ticker in step 1), Oil (ticker TBD — confirm
  in step 1, e.g. USO vs XLE mean different things and the choice should
  be deliberate, not default), US10Y, US5Y, US2Y, Shell (SHEL). **Verify
  each has the data it needs before promising it in the UI** — do not
  assume ETF/yield coverage exists just because equity coverage does.
- **Watchlist instruments are appended dynamically**, read live from the
  existing `GET /api/v1/watchlist` data path (reuse, don't re-implement).
  `source: "watchlist"` distinguishes them from the fixed seven so the UI
  can group or label them separately if useful.

## 3. Non-functional requirements

- **Cache aligned to the report's actual generation cadence** — this is
  a once-daily artifact (the bot posts it once), not live data. Don't
  apply the 30-second Data Source cache or the 5-minute candidates
  cache; a long TTL (e.g. until the next report generation, or a fixed
  several-hour window) is correct here and matches Backtest Lab's
  reasoning more than the live screens'.
- **Auth, CORS, loopback binding:** same posture as the rest of
  `momentum-api`.
- **No write path.**

---

## 4. Error responses

| Condition | Response |
|---|---|
| No report generated yet today | `200` with the most recent available report, plus `report_date` showing which day it actually is — same "don't imply freshness that isn't there" rule as `is_stale` elsewhere. Do not 503 for this; a market report from yesterday is still useful and should say so, not disappear. |
| An instrument's underlying data is missing | That instrument shows `unavailable_reason`; the rest of the response is unaffected. |
| DB unreachable | `503`, `{"error": "database_unavailable"}` |

## 6. Build order

| Step | Deliverable |
|---|---|
| 1 | **Verification, not optional.** Confirm: (a) `equity_ohlcv` coverage for the gold/oil ETF tickers and SHEL; (b) `macro_fred` coverage for 5Y and 2Y Treasury series (10Y is confirmed from the sample report; 5Y/2Y are not); (c) whether `marketcycle`'s compute function can already take a symbol parameter, or needs that change made; (d) whether intermarket correlations should run per-instrument at all, or stay as one market-wide reading (§1.1). Report back before writing any handler code — this step is where this addendum's actual scope gets decided. |
| 2 | If needed per step 1(c): parameterize `marketcycle` by symbol. This is a change to an existing, working package with a live Discord consumer — same care as the `data-fundamental` widening addendum in Phase 1 §8.4: don't regress the existing single-symbol report the bot already posts. |
| 3 | `GET /api/v1/market-report/today` handler |
| 4 | Tests per §5 |
| 5 | Point `mfe-market-report`'s fetch layer at it |

**This build order is longer than the other addendums' for a reason.**
Every prior addendum reused an already-working, already-parameterized
data path. This one may not have one yet for two of its seven
instruments and for the market-cycle metric generally. Step 1 finds out
which parts are a straightforward reshape and which parts are real new
work, before any UI gets designed against an assumption.
