# analyst-bot — known issues

Open defects in the bot, one row each. Fixed rows move to the commit that fixed them.

| Issue | Current state | Fix |
|---|---|---|
| **RSI action rule never counts RSI divergence or support/resistance** | `actions/rules/rsi.py` reads `indicators["rsi_divergence"]` (payload `divergence_type`) and `indicators["support_resistance"]` (payload `near_support` / `near_resistance`). technical-analysis writes `rsi_divergence_rsi14_sw5` (payload `bullish_regular`, `bearish_regular`, `kind`) and `sr_levels` (payload `support`, `resistance`, `support_touches`, `resistance_touches`, `current_price`). Neither lookup ever matches, so on live data only trend and the FA composite tier can add confluence: `rsi_oversold` reaches BUY_WATCH only with uptrend + strong FA, `rsi_overbought` reaches TRIM_WATCH only with downtrend + weak FA. Logged 2026-09-25 | Divergence: look up the `rsi_divergence_` prefix and read `bullish_regular` / `bearish_regular`. Support/resistance is not a rename: the worker stores levels, not "near" flags, so a proximity rule has to be defined (e.g. price within N% or N×ATR of the level) before the rule can use it. Independent of the heuristic-signals validation, which does not replay the RSI rule (it needs point-in-time FA tiers). Same class as the MACD lookup bug fixed in `fbaee0a` |
| **`test_momentum_scan` and `test_alert_scan` cannot run in the same process** | `scheduler/jobs/test_momentum_scan.py` installs stub modules into `sys.modules` at import (`db`, `db.queries`, `db.cache`, `db.queries.momentum`) so it can run without asyncpg/redis. Any test module imported after it in the same `unittest` run then gets the stub `db.queries` package, and `test_alert_scan.py` fails to import (`cannot import name 'fundamental' from 'db.queries'`). Each suite passes on its own, and `test_alert_scan` passes when it is listed first. Logged 2026-09-26, not urgent | Scope the stubs to the test (install in `setUpModule`/`setUp` and restore `sys.modules` afterwards, or use `unittest.mock.patch.dict(sys.modules, …)`), so suite order no longer matters. Until then, run `test_momentum_scan` in its own process |
| **VIX "elevated" band and the `vix_elevated` alert use different thresholds** | technical-analysis stores `vix_regime` with `compute.ClassifyVIX` bands (`elevated` above 20; `TECHNICAL_VIX_*`), and the actions engine classifies VIXCLS with hardcoded 35/20/12 bands. The bot's `vix_elevated` alert fires only above `BOT_VIX_ALERT_THRESHOLD` = 25. So VIX between 20 and 25 is labelled "elevated" everywhere (stored band, action rule, Stock Detail) with no alert and no warning severity. Pre-existing; logged 2026-09-25, not urgent | Pick one definition: either alert at the band's own boundary (20), or add a distinct band above 25 that the alert and §2.3 severity key on. Also read the engine's bands from the same config as `ClassifyVIX` instead of hardcoding them |
| **`vix_elevated` alerts are stored under an equity, not as market-wide** | `ReportBuilder.scan_alerts` checks `vix_regime` inside the per-symbol loop, so the alert carries `symbol` of whichever equity's scan saw VIX above `BOT_VIX_ALERT_THRESHOLD` first; its cooldown key is market-wide (`alert:vix_elevated:{interval}`) but the `fired_alerts` row (and the Discord embed) name that equity with `exchange_type` `equity`. Alarm History works around it by never linking `vix_elevated` rows and labelling them market-wide. No live row yet (VIX 14.2 on 2026-09-27). Logged 2026-09-27 | Detect VIX once per scan, outside the symbol loop, and store it as market-wide: a reserved symbol (e.g. `VIX`, matching the report's instrument) with a market-wide `exchange_type` (needs migration 026's `exchange_type` check widened, e.g. `market`), so readers can tell it apart without knowing the alert type |
